New optional host webhook `mcp_connection.revoked` (`settings.hostWebhooks.mcpConnectionRevoked`, from `OPENGENI_HOST_WEBHOOK_MCP_CONNECTION_REVOKED_URL` and `OPENGENI_HOST_WEBHOOK_MCP_CONNECTION_REVOKED_SECRET`). When an MCP connection is disconnected, or its access setting loses a permission or a workspace, the API starts one durable delivery through the workflow client's new optional `startHostWebhookDelivery` (the `hostWebhookDeliveryWorkflow` Temporal workflow) right before it writes the change; the worker POSTs `HostMcpConnectionRevokedWebhook` once it sees the change committed, signed `X-Host-Signature: sha256=<hex HMAC-SHA256(secret, body)>` with `X-Host-Delivery: <id>`, and retries the same body and id with backoff until the host answers 2xx. The worker looks for the committed change for about two minutes (24 checks, 5 seconds apart); a change that never commits sends nothing. A downgrade counts as committed once the stored setting has lost something against the one it started from, and the body carries the setting as it stands. Delivery goes through the pinned outbound transport: https outside local/test, a target inside the cluster allowed, redirects never followed (a 3xx or a 4xx other than 408 and 429 ends the delivery). A notification never blocks the change: when the delivery can't be started, the API logs one `host_webhook.delivery_start_failed` warning (event, organization, connection, delivery id, error class) and writes the change anyway, and the host MCP connection read stays authoritative. An API configured with the webhook but a workflow client without `startHostWebhookDelivery` refuses to start (`HOST_WEBHOOK_DELIVERY_UNAVAILABLE`). Unset, nothing is started and nothing changes. New exports `HostMcpConnectionRevokedWebhook`, `HostWebhookDeliveryRequest`, `isConsentScopeDowngrade`, `HOST_WEBHOOK_SIGNATURE_HEADER` and `HOST_WEBHOOK_DELIVERY_HEADER` (`@opengeni/contracts/organization-governance`) and `mcpOAuthConnectionConsentScope` (`@opengeni/db`).
